## Problem Statement

Agent trajectories are non-deterministic and nobody can say *why* one run
diverged from another. The whole observability category traces what happened;
none of it can answer the counterfactual, "what would this agent have done if
one thing had been different."

tiller is positioned to answer that, by accident. Because the driver emits a
quoted MFA term and every `{action, result}` pair lands in an ordered log,
tiller is event-sourced rather than checkpointed. The state at turn N is
`Enum.take(log, n)`. There is no checkpointer to configure and no per-step
snapshot cost, so every turn is a free fork point.

Build the instrument that exploits that: fork any turn into N branches, each
mutating exactly one variable, race them concurrently under the supervisor,
and report the first divergent event plus the smallest mutation that changed
the outcome.

Scope note: this is a learning project, chosen for fun. Adoption is not a goal.

## What Makes This Cool

- **Fork is free.** LangGraph Studio requires a compiled checkpointer or time
  travel does not work at all. tiller needs none, because the log prefix *is*
  the state.
- **Replay is deterministic.** LangGraph re-executes nodes on replay, LLM calls
  included, so results can differ. Replaying a recorded prefix with injected
  results does not.
- **Nobody races branches.** Every tool surveyed explores forks one at a time.
  N concurrent branches is `DynamicSupervisor.start_child` called N times, and
  a threading problem everywhere else.
- **Capability counterfactuals ship nowhere.** "What if the agent had not been
  allowed to call this tool at turn 3" appears in arxiv papers and in no
  product. In tiller the whitelist is already a per-session parameter
  (`lib/tiller/session.ex:22`), so the mutation axis costs a keyword.
- **Process kill as a mutation axis.** Only casual on the BEAM, though see
  Open Question 5 for why it is harder than it first looks.

## Constraints

- Weekend-scale project, though the chosen approach is honestly multi-weekend.
  No upper bound has been set; the go/no-go in The Assignment is the only gate.
- Elixir 1.20, currently zero dependencies. Phoenix/LiveView is an accepted,
  permanent change to that character (premise 5).
- No real LLM driver. FakeDriver is the contract and stays the contract.
- `Tiller.Tools` currently holds `echo/1` and `fail/0`. The counterfactual is
  meaningless until there are three or four genuinely different tools.
- **The existing test suite does not survive this.** 4 of the 5 tests in
  `test/tiller_test.exs` assert `{:halted, n} = Session.run(pid)` synchronously
  and pattern-match `State.log()` as bare `{action, result}` 2-tuples. Both
  contracts change. Only `"bad action term is rejected"` survives, because it
  calls `Actions.eval/2` and touches neither module. `Tiller.Demo` breaks for
  the same reason.

## Premises

1. tiller is event-sourced, not checkpointed. Forking needs no checkpointer and
   costs nothing per turn, because the prefix of the log IS the state.
2. **(REVISED)** Making sessions async and attributed is the main event, not
   setup. Originally estimated at ~30 lines; Codex read the source and put the
   runtime core at 90-140 lines and the Session/State inversion slice at
   250-400. Revision accepted. The specific miss: `spawn_subagent` calls
   `Tiller.Session.run/1` synchronously at `lib/tiller/actions.ex:59`, from
   inside the parent's own `handle_call(:run, ...)`, so the parent blocks on
   the child's entire run. Inverting the session loop alone does not fix this.
3. Concurrent N-way fork racing is the differentiator. Cheap on the BEAM,
   expensive in every tool surveyed.
4. Per-fork whitelist variation is a counterfactual nobody ships and is nearly
   free here.
5. Crowded space is not a disqualifier for a learning project. The deliverable
   is a striking demo and real understanding.

## Approaches Considered

- **A: Vertical Slice.** Codex's minimal plan, branches vary by driver.
  Rejected: branches differing only by which script you handed them shows
  concurrency, not insight.
- **B: Event Core First.** Foundation with tests before any UI. Rejected:
  nothing on screen until late, the standard way a fun project dies.
- **C: Whitelist Butterfly.** One mutation axis (capability), same cost as A.
  Rejected in favor of D, but remains the documented fallback if D proves
  intractable.
- **D: Full Butterfly Lab.** Chosen. See below.

## Recommended Approach

**D: Full Butterfly Lab.** Effort XL, risk High.

A first-class `Tiller.Mutation` vocabulary applied per-branch, raced
concurrently, with automatic divergence analysis.

### Mutation axes

| Axis | Mechanism | Cost | Tier |
|---|---|---|---|
| Whitelist restriction | `whitelist:` keyword to `Session.child_spec` | already plumbed | MVP |
| Driver swap | `driver:` keyword | already plumbed | MVP |
| Result override | Replay driver injects a different recorded result | small | Stretch |
| Injected latency | `Process.sleep` in the turn scheduler | small | Stretch |
| Process kill / restart | see Open Question 5 | **High, not medium** | Stretch |

### Types

These need to exist before anyone writes `Tiller.State` or `Tiller.Mutation`.

```elixir
@type action :: {:call, module, atom, [term]}

defmodule Tiller.Event do
  defstruct [:seq, :session_id, :parent_id, :turn, :action, :result]
end

@type event :: %Tiller.Event{
        seq: pos_integer,             # monotonic, globally ordered
        session_id: binary,           # this branch
        parent_id: binary | nil,      # branch ancestry; nil for root
        turn: non_neg_integer,        # turn index within this session
        action: action | :halt,
        result: {:ok, term} | {:error, term} | {:halted, non_neg_integer}
      }

# Halt records: action is the atom :halt, result is {:halted, turn_count}.
# This replaces the current s.state.append(:halt, s.turns) at session.ex:51.

@type mutation ::
        {:whitelist, [{atom, arity}]}
      | {:driver, module, ctx :: term}
      | {:result_override, turn :: non_neg_integer, term}
      | {:latency, milliseconds :: pos_integer}
      | {:kill_at, turn :: non_neg_integer}
```

### Foundation API

```elixir
Tiller.Session.run(pid)                              :: :ok
Tiller.Session.await(pid, timeout \\ 5_000)          :: {:halted, non_neg_integer} | {:error, :timeout}
Tiller.Session.fork(pid, turn, mutation, opts \\ []) :: {:ok, pid}
Tiller.State.append(session_id, parent_id, turn, action, result) :: {:ok, event}
Tiller.State.events(session_id)                      :: [event]
Tiller.State.subscribe(session_id)                   :: :ok
```

`await/2` exists specifically so the test suite and `Tiller.Demo` can still
assert deterministically once the loop is async. It is built on
`State.subscribe/1`, not on a sleep.

### Foundation work

- `Session.run/1` becomes a `cast`, one turn per scheduled message, so the
  process is observable mid-run.
- `spawn_subagent` stops calling `Session.run/1` synchronously
  (`lib/tiller/actions.ex:59`).
- Events carry `session_id`, `parent_id`, `turn`, and a monotonic sequence.
- `Tiller.State` becomes an ordered event store with per-session filtering,
  replacing the single global list. Fix `log ++ [event]` (O(n) per append,
  `state.ex:33`) at the same time.
- `Phoenix.PubSub` broadcast on append.
- A minimal LiveView tail on the event stream, enough to prove events arrive
  live. The 3-pane inspector is Next Step 9, not part of this.

`Tiller.Driver.Replay` is deliberately NOT in the list above; it is tracked as
Next Step 7 and gated on Open Question 2.

**Effort scope, stated precisely:** the 250-400 line figure covers the
Session/State inversion, attribution, PubSub, and a minimal LiveView tail.
It does **not** cover `Tiller.Mutation`, `Tiller.Driver.Replay`, the
divergence algorithm, the 3-pane UI, or fault injection. Approach D as a
whole is not costed and is honestly multi-weekend.

Rationale: it is the only version that turns the screen from a spectacle into
an instrument, and the divergence analysis is the part that makes it worth
building rather than watching. Chosen against the recommendation (C), knowingly.

## Open Questions

1. **Is divergence detection tractable?** Aligning two sequences of quoted
   terms is the one genuinely algorithmic piece and nothing else in the design
   is hard. Unresolved. This is what The Assignment attacks.
2. **How does `Tiller.Driver.Replay` hand off to its delegate?** Driver `ctx`
   is opaque and driver-specific: `FakeDriver`'s is `%{queue: [...]}`, a real
   driver's will hold conversation state. Replay cannot construct a delegate's
   ctx from recorded events. Two candidate answers: require the delegate's
   initial ctx be supplied at fork time, or add an optional
   `Tiller.Driver.resume_ctx(events)` callback. Undecided. Blocks Next Step 7.
3. **What does "smallest mutation" mean when axes are incommensurable?** A
   whitelist removal and 200ms of latency are not on the same scale. Options:
   rank within an axis only, or hand-assign weights. Undecided.
4. **How do 32 branches lay out on one screen?** Flagged as a serious problem
   by both models, solved by neither. Explicitly Stretch, not part of Done.
5. **Process kill is not a resume.** `DynamicSupervisor`'s default
   `:one_for_one` restart re-invokes the child's original `child_spec` start
   args, so a killed branch comes back with its *initial* ctx and `turns: 0`.
   That is a fresh duplicate branch, not a branch resumed from the kill point.
   Resuming requires capturing and re-injecting mid-run state, which is another
   Replay problem. This is why the axis is costed High. Must be resolved before
   Next Step 10.

### Resolutions (2026-09-06)

1. **Tractable.** `Tiller.Divergence.first_diff/2` is five function clauses
   over `Tiller.Event.key/1`; the spike passed well inside the budget.
2. **Snapshots.** A session parks its driver context and tool state in
   `Tiller.State` before every turn, so a fork already has the delegate's
   context at the fork turn. Option 1 (context supplied at fork time) with
   the supplying done by the session itself; no `resume_ctx/1` callback.
3. **Measure the effect, not the mutation.** A mutation is *decisive* if the
   branch ends somewhere else (different last action or result, or a
   different turn count). Among decisive branches the smallest is the one
   whose trajectory differs from the original in the fewest turns
   (`Tiller.Divergence.distance/2`), later first divergence breaks ties, and
   `Tiller.Mutation.size/1` breaks ties only within one axis. No cross-axis
   weights. See `Tiller.Race`.
4. **Grid.** The race pane is a branch-by-turn table: one row per branch,
   one cell per turn coloured same, different, extra or missing. Rows are
   ranked per (3), the smallest decisive mutation is starred, clicking a
   cell selects that turn, clicking an id shows that branch's card.
   *Amended 2026-09-07:* the grid holds a wide race without changing
   shape, so `Tiller.Mutation.sweep/4` generates one instead of relying on
   hand-picked presets: a branch per tool the run still uses after the
   fork point, per replayed turn, per turn it could die at, plus latency
   and a control, capped at 24 by taking from each axis in turn: a long
   run reaches many points on every axis and each branch costs a row of
   cells, so an uncapped sweep grows with the square of the run. Ten
   branches on the demo run rank without crowding, so no separate summary
   view is needed.
5. **Resume, and show the hazard.** Because snapshots live in the store, a
   restarted session resumes at the turn that was in flight with the same
   id and turn counter, and a branch's tool state (under
   `Tiller.ToolStates`, unlinked from the session) survives the kill.
   `kill_at N` runs the tool at turn N and dies before logging it; the
   restart runs it again. The log shows the action once and the world saw
   it twice, which is the at-least-once hazard of supervised agents.

## Success Criteria

**MVP (this is "Done"):** pick a turn in a recorded run, fan out to at least 4
branches across the two already-plumbed axes (whitelist, driver), watch them
finish at different times in one LiveView, and have `Tiller.Divergence` report
the turn at which they first diverged.

**Stretch (explicitly not required for Done):** the `result_override`,
`latency`, and `kill_at` axes; 32 concurrent branches and the layout problem
that comes with them; ranking by smallest decisive mutation. *All shipped as
of 2026-09-06; see Resolutions above.*

Deliberately out of scope entirely: auth, generic serialization,
production styling. (Real LLM drivers and persistence across restarts
were out of scope for the MVP and have since been built:
`docs/designs/llm-driver.md` and `Tiller.State.Log`.)

## The Assignment

Before touching `Session` or `State`, spend 30 minutes writing
`Tiller.Divergence.first_diff/2` over two hand-written lists of quoted terms.

```elixir
@spec first_diff([event], [event]) ::
        :identical
      | {:diverged, index :: non_neg_integer, left :: event | nil, right :: event | nil}
# left or right is nil when one branch ran out of turns first.
```

Three test cases: identical prefixes then a different tool, identical actions
with different results, and one branch halting early. No GenServers, no
Phoenix, no async. Just the function and `mix test`.

This is the only genuinely algorithmic piece in the whole design and everything
else is plumbing you already know how to write. If it is obviously right inside
30 minutes, D is real and you should build it. If you are still fighting
alignment semantics at minute 45, D is a multi-weekend project wearing a
weekend costume, and the honest move is to drop to approach C, the whitelist
butterfly, which needs no divergence analysis to be interesting.

Do the spike first. It is a go/no-go, and it costs half an hour.
